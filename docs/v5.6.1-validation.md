## Memory estimate audit

Every local GGUF that the selected runtime can load was started from its
AutoTuner plan (Auto context, vision as scanned, no draft, no prompt cache),
answered one request and was then measured: per-process dedicated/shared GPU
memory (Windows "GPU Process Memory" counters), working set, private bytes and
USS. The same servers report their own buffer sizes at `-lv 4`.

### Before (v5.6.0 planner, Vulkan, Q8_0 KV, 66 loads)

| Plan class | n | GPU real − estimate, GiB (mean [min … max]) | Host estimate | Host real |
|---|---:|---|---|---|
| dense, one GPU | 25 | −0.08 [−1.32 … +1.29] | 0.00 | RSS 8.4 mean (= model file), USS 0.6 |
| dense, split over two GPUs | 16 | **+2.25 [−1.63 … +9.99]** | 0.00 | RSS 23.0 mean, USS 3.9 (max 7.9) |
| MoE, one GPU | 9 | −0.21 [−2.25 … +1.07] | 0.00 | RSS 14.9 mean, USS 0.7 |
| MoE, split over two GPUs | 12 | **+2.26 [−1.83 … +5.32]** | 0.00 | RSS 30.6 mean, USS 4.5 (max 11.0) |
| MoE hybrid (CPU experts) | 4 | −2.98 [−4.70 … −1.34] | 14.4 mean | RSS 32.5 (mmap), USS 4.2 |

22 of 66 plans used more than 1 GiB above the estimate, 10 more than 3 GiB;
the worst was Spark-X2.5 at 1,048,576 context (+9.99 GiB). On split plans up
to 11 GiB went into *shared* GPU memory.

### What was wrong

Component by component (`-lv 4`), weights, KV (BF16, Q8_0 and Q4_0) and
recurrent state matched the estimate. Three things did not:

1. **Compute buffers were not estimated.** llama.cpp reserves the attention
   mask (context × ubatch, F16) about twice on one device and about ten times
   when layers are split across devices, plus activations (about 46 bytes per
   ubatch token and embedding dimension). At 262,144 × 1024 that is 1.0 GiB on
   one GPU and 4.4–6.0 GiB on two; at 1,048,576 it was 16.4 GiB. The host
   keeps about 1.1 (single) or 4.3 (split) masks as staging memory.
2. **mmap on Windows.** Fully offloaded plans kept the whole model file in the
   server's working set; system "RAM in use" rose by the file size (13–33 GiB)
   although the estimate said 0.
3. **Two KV formulas.** MLA models (`deepseek2`: GLM-4.7-Flash, DeepSeek) have
   no V cache — the estimate was 1.95× too high. gpt-oss alternates
   sliding-window and dense layers — the estimate counted all 24 layers
   instead of 12 (2.0× too high).

### Changes

- `compute_buffer_estimate_gb` adds `Compute GPU` / `Compute RAM` (mask copies
  + activations, host staging, fixed 0.4 GiB runtime, CPU-side input
  embeddings) to every footprint total in GUI, TUI, preflight and registry.
- A split plan that would not fit with these buffers halves `-ub` (not below
  256 or a Gemma 4 projector's 1120); if it still does not fit, Auto context
  shrinks until it does. An explicit context is never changed.
- Windows, all weights on GPU, load mode left on Auto: `--load-mode none`.
  Qwen3.8-27B UD-Q4_K_XL: working set 16.4 → 1.8 GiB, load 17.3 → 15.2 s,
  31.6 → 31.1 tok/s. Ornith-35B on two GPUs: 28.5 → 2.8 GiB, 23.8 → 18.8 s,
  124.1 → 124.7 tok/s. Hybrid plans, lazy tables, mlock, unified memory,
  Linux and an explicit Expert load mode are unchanged.
- MLA KV counts K only; gpt-oss counts its dense half. GLM-4.7-Flash now
  plans its full 202,752 context with BF16 KV (was 185,344 at ubatch 256).

- **GPU estimate:** on Vulkan no measured plan uses more than the estimate
  plus 1 GiB (83 rows: mean −1.40, worst +0.52). On HIP 3 of 94 rows do, all
  Gemma 4 with its two attention masks (worst +1.49 GiB; mean −0.93). Before,
  22 of 66 Vulkan plans exceeded the estimate by more than 1 GiB, by up to
  9.99 GiB. The estimate now errs on the safe side, most on plans that
  already carried placement reserves.
- **Host memory of fully offloaded plans:** working set ≈ USS ≈ estimate
  (largest RSS − USS gap 0.05 GiB), instead of 0 estimated against 8–31 GiB
  resident. On two-GPU Vulkan plans the host still holds up to 2.7 GiB more
  than estimated where the driver places part of a GPU buffer in shared
  memory; HIP stays 1.1–1.8 GiB *below* the estimate there.
- **KV types:** BF16, Q8_0 and Q4_0 track llama.cpp's KV report on every
  class (for example Ministral-3-14B at 262k: 22.00 estimated / 21.25 real
  with Q8_0, 27.03 / 27.03 with BF16, 12.80 / 11.25 with Q4_0). The Q4 factor
  is deliberately a little conservative.
- **Hybrid note (CPU-resident weights):** the host estimate matches
  llama.cpp's own CPU-side buffers — pinned to the 16 GB card, Qwen3.8-27B Q8_0
  (dense hybrid, 32 of 65 layers on GPU) reports 14.42 GiB against 15.10
  estimated with Q8_0 KV, 15.22 / 15.99 with BF16 and 14.41 / 15.10 with Q4_0;
  Gemma 4 31B 9.47 / 9.06; Qwen3.6-35B-A3B Q8 (MoE hybrid) 25.58 / 24.95. The
  Windows working set is larger (25–33 GiB) because these plans keep mmap and
  the pages read for the GPU upload stay mapped; that share is file-backed and
  reclaimable. USS is only 0.6–5.7 GiB.
- **Plans changed by the new rules, re-measured (Vulkan):** Devstral-Small 2
  24B (two GPUs, 393k context, ubatch 512): shared GPU memory 7.8 → 3.8 GiB;
  Nemotron 3 Nano Omni: Auto context 1,048,576 → 871,424 at ubatch 256,
  shared 11.0 → 4.7 GiB; North-Mini-Code: ubatch 512, shared 8.0 → 4.6 GiB;
  Qwen3.8-27B Q8_0: ubatch 256 at the full 262,144 context. Estimates for
  these runs are 0.5–4.4 GiB above the dedicated GPU memory. GLM-4.7-Flash and
  gpt-oss: KV estimate 5.62 / 5.43 real and 1.65 / 1.61 real (was 10.62 and
  3.30).
- **Not an estimate problem:** Maple-Preview TQ2_0 runs its ternary weights on
  the CPU with HIP (1.85 GiB of GPU memory against 6.91 planned, 5.9 GiB host);
  Vulkan places them on the GPU as planned. Forcing Q8/Q4 KV on Unlimited-OCR
  fails by design (its profile disables flash attention; Auto uses F16).

Limits: one request per load, so buffers that only grow under long prompts
are not covered; the split factor was measured on two AMD cards with Vulkan
and HIP and is an empirical model of the scheduler, not a guarantee for other
device counts or backends. Fork runtimes, DiffusionGemma, VoxCPM2, K2 Horizon,
Agnes, Bonsai 2 and Xing were not loadable on stock b11371 and are not part of
the audit; the local Hy-MT2-30B-A3B Q6_K file fails on b11249…b11371 alike
(`wrong number of tensors; expected 766, got 719`, an outdated conversion).
