# AutoTuner v5.5.3 validation

Local checks: **2026-09-19**, Windows x64, Python **3.14.5**. Runtimes under
test: the unchanged **b11042** HIP and Vulkan mainline trees from the
[b11042 audit](llama-b11042-audit.md) (llama.cpp itself was not re-audited:
this release adds no mainline build) and the new **ROCmFPX** fork trees
`fpx_b11544_{vulkan,hip}_llama.cpp` built by the new
`rocmfpx_{vulkan,hip}_llama_build.ps1` recipes (fork main commit
`aed0d5fd9`, 2026-09-06; fork build number 11544; mainline merge base
b10766).

This release adds the `agnes-3_0-flash.yaml` profile for Agnes-3.0-Flash
Preview (Agnes AI, 33B dense hybrid, `qwen35` conversions), the ROCmFPX
tensor-type gate (`__ggml_types__` header scan + `_rocmfpx_block_reason`),
the two fork recipes with the `-PatchFiles` mechanism and the RDNA4 MMQ
patch, and honours an explicit profile `draft_p_min: 0.0` when the command
is built. The planner's placement, KV and speculative logic did not change.

## Does mainline load Agnes-3.0-Flash?

- The Agnes checkpoint (`model_type: agnes`, 72 layers = 54 gated delta-rule
  + 18 global attention, parallel SwiGLU 2048 branch in every layer) has no
  architecture in mainline llama.cpp (no hit in `llama-arch.cpp` or
  `convert_hf_to_gguf.py` on master, 2026-09-19). Every community GGUF is a
  `qwen35` conversion: kingjones777, 0xKitkat and ngquocvinh fold the parallel
  branch into the standard MLP (width 19,456) and load on any qwen35-capable
  build; jakeatx and quimmedes keep `ffn_*_par` tensors and need their forks.
- kingjones777's `Agnes-3.0-Flash-Preview-MTP-ROCmFP4-imatrix-GGUF` files are
  additionally quantized with the ROCmFPX fork's reserved ggml types. Real
  headers (scanner on the downloaded files): `general.architecture = qwen35`,
  73 blocks incl. the NextN MTP block, `general.file_type` 106 (STRIX_LEAN =
  92 `q4_0_rocmfp4` + 473 `q4_0_rocmfp4_fast` tensors, 18.06 GB) and 102
  (COHERENT = 565 `q4_0_rocmfp4`, 19.08 GB), BF16 mmproj.
- `agnes_negative.py` started the raw servers (`-ngl 99 -c 4096`) on the
  mainline b11042 trees: both exit 1 after 2.5 s with
  `gguf_init_from_reader: tensor 'blk.0.attn_gate.weight' has invalid ggml
  type 101. should be in [0, 43)`. The upstream CPU-only PR #24185 is still
  open. AutoTuner's own verdict for the same binaries
  (`check_model_build` on the real headers) refuses both files before
  launch with the same numbers in the message; the marker `rocmfp` (the
  fork's file-type name "ROCmFP4 Strix Lean" in its llama library) is
  absent from all seven local mainline, prism and TurboQuant binaries and
  present in both new fork binaries.

## Agnes-3.0-Flash on the workstation (fork fpx_b11544)

`agnes_test.py` drives AutoTuner's real planner (profile match, build gates,
`compute_config`, `build_command`) per backend × tier with the BF16 mmproj,
32k context and Q8/Q8 K/V; the planner pinned the R9700 on both backends
(`GGML_VK_VISIBLE_DEVICES=1` / ROCm0), offloaded 74/74 layers and used the
in-file MTP head (`--spec-type draft-mtp --spec-draft-n-max 4
--spec-draft-p-min 0.0`, `--jinja`, `--mmproj`). Prompts with thinking off:
`17 * 23` (expects `391`), the list `1 … 80` (231 generated tokens for the
decode figure, 184 of 184 drafted tokens accepted), the colour of a red
448×448 PNG (expects `red`).

| Backend × tier | Placement | Text | Bench decode / prompt | Image |
|---|---|---|---|---|
| HIP × STRIX_LEAN (patched) | 16,381 MiB on ROCm0, 834 MiB host | `391` | **67.2 t/s** / 108 t/s | `Red` |
| HIP × COHERENT (patched) | 17,186 MiB on ROCm0, 995 MiB host | `391` | **66.7 t/s** / 97 t/s | `Red` |
| Vulkan × STRIX_LEAN | 16,381 MiB on Vulkan0 (R9700), 834 MiB host | `391` | **28.7 t/s** / 67 t/s (spec off: 23.6 / 49) | `Red` (spec on and off) |
| Vulkan × COHERENT | 17,186 MiB on Vulkan0 | `391` | 5.0 t/s / 69 t/s (two runs) | `Red` |

- Image requests succeed with the MTP head loaded on both backends; the
  model card's "image requests fail with MTP" finding applies to the older
  charlie12345 build (`d3ca537`) it measured, not to fork main `aed0d5fd9`.
- COHERENT is as fast as STRIX_LEAN on HIP but five times slower on Vulkan:
  it consists only of dual-scale `q4_0_rocmfp4` tensors, whose Vulkan
  mul_mat_vec shaders are much slower than the `_fast` variant STRIX_LEAN
  mostly uses. The profile note says so; AutoTuner does not pick a backend.
- Unpatched HIP: the first prompt batch aborted with `J_best=0` at
  `ggml/src/ggml-cuda/mmq.cuh:1648` (server exited, connection reset). The
  fork's ROCmFPX MMQ fallback table (PR #20 for issue #17) is included only
  from `mmq-config-rdna3.cuh`; `mmq-config-rdna4.cuh` (gfx1200/gfx1201) has no
  ROCmFPX entries. `patches/rocmfpx-rdna4-mmq-fallback.patch` routes the
  RDNA4 selector to the same fallback; the incremental rebuild took 3 min
  and both tiers then passed. No upstream issue was filed yet.

## Unit regressions (`test_agnes_3_0_flash.py`, 23 tests)

- Profile: every community filename spelling (kingjones777 tiers,
  0xKitkat/ngquocvinh `Agnes-3.0-Flash-Q4_K_M`, abliterated, quimmedes XYZ,
  underscore/compact spellings) matches `agnes-3_0-flash.yaml` even with
  `qwen35` metadata; plain Qwen3.5, opaque qwen35 re-quants, Ornith 1.5 and
  Bonsai 2 keep their profiles. Contract: 262,144 context, Q8 KV,
  throughput target, temp 1.0 / top-k 20 / top-p 0.95 / presence 0 (coding
  0.6), `draft_max 4`, `draft_p_min 0.0`, `--jinja --reasoning-preserve`, no
  arch fallback, no build gate, no marker. Every language pack names
  ROCmFPX, qwen35, PR #24185 and `ffn_*_par`.
- `_profile_draft_p_min`: Agnes and Nemotron 3.5 give 0.0, Qwen3.5 0.75,
  missing/unparsable/negative/>1/NaN fall back to 0.75.
- Scanner: a GGUF header with tensors of types 14/100/0/100/8 yields
  `__ggml_types__ == [0, 8, 14, 100]` and a complete scan; an empty header
  yields `[]`.
- Gate: STRIX_LEAN (106, types 100+101), COHERENT (102), Q8_0-ROCmFPX (111,
  type 103) and its AGENT tier (115) are refused when the marker scan fails,
  with the tensor names, tier, "invalid ggml type 100/101. should be in
  [0, 43)", the fork, PR #24185 and the mainline alternative in the message
  and no build probe; `file_type` alone refuses a shard without a tensor
  scan; a fork runtime allows the file and reports its build; ordinary
  GGUFs, 0xKitkat's Q4_K_M, mainline's MXFP4/NVFP4/Q1_0/Q2_0 and the
  PrismML range never trigger the scan.
- Command: fork binary, `--jinja`, `--mmproj`, no `-md`, `draft-mtp`,
  `--spec-draft-n-max 4`, `--spec-draft-p-min 0.0`, temp 1.0 / top-p 0.95 /
  top-k 20, 32k context on a 32 GB card.
- Recipes: both ROCmFPX scripts pin `aed0d5fd9…`, `-FixedIdentity "b11544"`,
  `FolderPrefix "fpx_"`, name b10766 and the RDNA4 patch; the patch touches
  `mmq-config-rdna4.cuh` with the include and the fallback return; the
  common helper carries `-PatchFiles`, the apply and the reverse check;
  `build_all_windows_llama.ps1` lists the pair.

## Observed, not changed

- The fork's `--version` reports its own rev-list count (11544) while its
  upstream feature set is that of b10766; AutoTuner's numeric gates
  therefore treat the fork as newer than b11042. None of the gates that
  matter for Agnes (NextN array regression b10741–b10748, Nemotron latent
  MTP b11025, Maple b10964) is affected by the ROCmFPX files, but a build
  number from a fork is not a mainline feature level.
- The experimental Vulkan cooperative-matrix path for ROCmFP4
  (`GGML_VULKAN_ROCMFP4_COOPMAT`, runtime `GGML_VK_ROCMFP4_COOPMAT`) stays at
  the fork's default (off) and was not measured.
- The follow-ups recorded in [v5.5.2](v5.5.2-validation.md) are unchanged.

The publication gates (main CI on Python 3.10–3.14 across Windows, Ubuntu,
macOS and six Linux distributions, the tag workflow's native ZIP builds and
smoke tests, digest/architecture verification of the published assets) are
the same as in [v5.5.2](v5.5.2-validation.md).
