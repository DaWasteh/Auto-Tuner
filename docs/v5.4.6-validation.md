The failed image+DFlash2 combination is **not counted as a passing inference
test**. It fails because the draft context rejects nonconsecutive positions
(X=3, Y=18) after the pinned image batch is skipped. v5.4.6 rejects this
specific b10901/qwen35/DFlash2/vision combination **before launch**, with a
message to disable Draft for images or Vision for text-only drafting.
Regression tests assert the guard and both alternatives; no silent fallback.

The 26.8222-GiB lazy table was located by its GGUF tensor offset inside shard 2.
Windows mapping/working-set APIs measured the exact **28,800,138,240-byte**
table range: **266,240 resident bytes** at readiness in each run. Whole-process
RSS was 20.705 GiB (Vulkan) / 29.330 GiB (HIP). Whole-process RSS is not table
residency. These are point-in-time observations, not hard residency limits or
long-context stress tests.

## New-model evidence and regression coverage

- **DeepSeek-V4.1-Flash:** official architecture/config and conversion PR checked;
  **no inference support claimed**. Filename aliases, proposed architecture
  fallback, old `deepseek4` Engram conversions, generic custom profiles, target
  and draft command paths all reject unsafe use. Original V4 remains unchanged.
- **Nex-N2.5-mini:** official config and sampling checked. Actual b10901
  `/apply-template` validates default, medium, none and high reasoning suffixes
  plus a tool prompt, using the official Nex template.
- **GLM-5.3-CYBERSECURITY-FP8:** architecture configs byte-identical to base;
  generation penalty and template defaults differ. Actual `/apply-template`
  confirms base history preserves a marked reasoning span and the derivative
  drops it with `--no-reasoning-preserve`.
- Template tests use a small **CPU-loaded surrogate model solely to host the
  renderer**, not Nex/GLM inference. New Nex/GLM weights were not installed.
- Existing Qwen/GLM architecture fallbacks and GLM-5.3-Flash stay separate.
- Removed loading switches, explicit lazy policy, old-runtime compatibility,
  conservative qwen4exp indexer reserve and profile CLI options remain covered.

Two early local test iterations had test-fixture issues (constructing an
incomplete `TunedConfig`, and an assertion expecting a different word in the
block message). These were corrected; the complete suite above passes. The
image+DFlash2 failure was a separate real runtime finding, not a fixture error.

## Publication gates and limits

The local build precedes push. The annotated **v5.4.6** tag is created only
following successful main CI: Ruff, Python **3.10–3.14** on Windows, Ubuntu
and macOS, plus Fedora, Arch, Mint, CachyOS, Kali and Debian source tests.
The tag workflow builds native Windows x64, Linux x64 and macOS arm64 ZIPs,
smoke-tests them and launches the same generic Linux ZIP on seven distributions
before publication. Published ZIPs are then checked for architecture, executable
bits and GitHub SHA-256 digests. CI's Windows EXE is independently built with
Python 3.12 and need not match the local EXE hash.

No CUDA/Metal/iGPU inference, complete llama.cpp compiler rebuild, new-model
weight inference, or universal long-context/performance guarantee is claimed.
The qwen4exp planner intentionally retains an old-runtime-compatible indexer-V
reserve, so b10901 may have more capacity than the conservative plan exposes.
Linux/macOS packaging CI is not GPU-inference validation. macOS is a community
build without Apple notarization: Finder right-click → Open / Privacy & Security
→ Open Anyway may be required.
