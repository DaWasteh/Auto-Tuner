## Fix: default build after a replaced build

While validating the frozen EXE, a fresh data directory selected
`2b_b10743_vulkan_llama.cpp` — the Ternary/Bonsai Prism fork — as its
llama.cpp runtime. The build list is ordered by family name and `2b_llama`
sorts before plain `llama`; whenever no saved choice applied, the GUI and the
CLI simply took entry 0. The user's own tray instance was affected the same
way: its saved build `b11224_vulkan_llama.cpp` had been replaced by b11249,
so every model would have run on the b10743-based fork. `_default_fork_index`
now keeps an existing saved build, maps a missing one to the newest build of
the same family and backend, and otherwise takes a bare legacy `llama.cpp`
checkout or the newest mainline build (Vulkan before HIP, numbered builds
before stable releases). The display order and explicit choices are
unchanged; a profile that needs a fork (Bonsai, Agnes) still switches to it.

`fork_default_live.py` starts the real GUI with an isolated data directory
against the 13 local trees, reads the fork log line and closes the window:

| Scenario | v5.5.8 EXE | v5.5.9 |
|---|---|---|
| Fresh settings (auto-discovery) | `2b_b10743_vulkan_llama.cpp` | `b11249_vulkan_llama.cpp` |
| Active path `L:/LAB/ai-local`, saved `b11224_vulkan` (deleted) | `2b_b10743_vulkan_llama.cpp` | `b11249_vulkan_llama.cpp` |
