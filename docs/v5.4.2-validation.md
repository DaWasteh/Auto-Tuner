# AutoTuner v5.4.2 validation

Validation date: 2026-09-05

## Scope

This release fixes two closely related desktop-lifecycle problems: an
AutoTuner that appeared to keep running after its window was closed, and the
possibility to start any number of AutoTuner GUI instances. The llama.cpp
authority is unchanged: stock b10797 (commit `832fd6f17`), audited in
[`llama-b10797-audit.md`](llama-b10797-audit.md); no profile, flag, or loader
contract changed, so no new upstream range was reviewed.

## Diagnosis

The "leftover instance" was reproduced against the shipped v5.4.1 binary and
the source launcher with a small harness that starts the GUI, waits for the
main window, posts `WM_CLOSE`, and watches the process tree:

| Scenario (v5.4.1) | Result |
|---|---|
| `qt_launcher.py`, *Hide on close* off, close after 8 s | process exits with code 0 within 1.5 s |
| `dist/AutoTuner.exe` (v5.4.1), *Hide on close* off, close after 8 s | bootloader and child exit with code 0 within 1.5 s |
| `qt_launcher.py`, close 0.3 s after the window appears (hardware probe still running) | exits with code 0 within 1.5 s |
| Any of the above with *Hide on close* **on** | window hides, process keeps running (by design of the v4.9.4 option) |

The user's `autotuner_settings.json` has `minimize_on_close: true`. Windows 11
places new notification-area icons in the hidden overflow menu, so the hidden
AutoTuner had no visible trace, and the next double-click on `AutoTuner.exe`
started a second copy. The console log confirms this sequence: the log of the
11:00 session contains the header of a 12:01 session, because
`autotuner_console.log` could not be rotated while the first process still
held it open, and the second control-API server failed on the occupied port.

Two further weaknesses were found on the way:

- `_request_quit()` relied on `quitOnLastWindowClosed`. A window that is
  already hidden in the tray is not "the last visible window" for Qt, so
  *Quit* from the tray menu could leave the event loop running.
- One run of the new desktop test, executed while the full suite loaded the
  machine, ended with exit code `0xC0000409` (fail-fast abort) instead of 0:
  the interpreter tore down while a worker thread was still alive. Six later
  runs, with and without load, exited 0; the abort is timing-dependent.

## Changes

- **`single_instance.py`:** `SingleInstanceGuard` listens on a `QLocalServer`
  named after a hash of the user and the resolved data folder (named pipe on
  Windows with `UserAccessOption`; `$TMPDIR` socket on Unix, stale files are
  removed only after nobody answered). The secondary launch connects with
  short retries (a named-pipe server re-arms its next instance from the event
  loop, and `QLocalSocket` does not retry `ERROR_PIPE_BUSY` on its own),
  grants the foreground right with `AllowSetForegroundWindow`, sends
  `activate`, waits until the outgoing buffer is empty, and disconnects. The
  primary emits `activate_requested`. `AUTOTUNER_ALLOW_MULTIPLE_INSTANCES=1`
  disables the guard.
- **`qt_launcher.main()`:** acquires the guard right after `QApplication`,
  redirects a second launch to the running instance and returns; connects
  `activate_requested` to `MainWindow._activate_from_other_instance()` (restore
  from tray, un-minimise, raise, activate, `QApplication.alert`, keeping a
  maximised window maximised); releases the lock on `aboutToQuit` and after
  `app.exec()`.
- **`MainWindow._request_quit()`:** calls `QApplication.quit()` after a
  successful `close()`.
- **Shutdown path after `app.exec()`:** `_drain_background_work()` asks every
  QThread parented to the main window to quit and waits up to 10 s; if a
  QThread or a non-main Python thread is still alive, the process ends via
  `os._exit(code)` after flushing the console log instead of running an
  interpreter teardown that would abort. `_arm_exit_watchdog()` additionally
  ends the process 15 s after the event loop finished should teardown hang.
- `build_exe.py` lists `single_instance` as a hidden import; PyInstaller pulls
  `PyQt6.QtNetwork` through its PyQt6 hook.
- README: feature bullet, environment-variable rows (`AUTOTUNER_DATA_DIR`,
  `AUTOTUNER_ALLOW_MULTIPLE_INSTANCES`), and the v5.4.2 changelog entry.

## Tests

`test_single_instance.py` (new):

| Test | What it pins down |
|---|---|
| `test_instance_key_is_stable_per_data_dir_and_safe_as_socket_name` | same folder → same key, relative spelling → same key, different folder → different key, name is pipe/socket safe |
| `test_multiple_instances_override_parses_like_a_boolean` | `0/false/no/off/empty` keep the guard on |
| `test_second_guard_is_refused_and_activation_reaches_the_primary` | second guard in the same process is refused, `activate` reaches the primary exactly once, connection without a command does nothing, `release()` frees the name |
| `test_notify_without_a_running_instance_fails_fast` | no primary → `False` in well under 5 s |
| `test_guard_is_honoured_across_processes` | child process owns the lock, parent is refused, activation makes the child exit 0 and release the lock |
| `test_close_without_tray_option_closes_the_window` | plain X closes |
| `test_close_with_tray_option_hides_and_quit_from_tray_ends_the_event_loop` | X hides into the tray, then `_request_quit()` ends a running `app.exec()` (8 s watchdog stays silent) |
| `test_activation_restores_a_tray_hidden_window` | hidden → visible; visible + maximised stays maximised |
| `test_gui_process_exits_after_closing_the_window` (opt-in) | real GUI process, `WM_CLOSE` 4 s after the window appears, exit code 0, no child left in the process tree |
| `test_second_launch_restores_a_tray_hidden_instance_and_exits` (opt-in) | first GUI hidden by X with *Hide on close*, second launch exits 0 and the first window is visible again |

The opt-in tests need a Windows desktop session (`AUTOTUNER_GUI_PROCESS_TESTS=1`);
`AUTOTUNER_GUI_PROCESS_BINARY=<path>` runs them against a frozen binary.

## Behaviour summary for users

- X with *Hide on close* **off**: the process ends.
- X with *Hide on close* **on**: the window goes to the notification area,
  the tray balloon says so, and a second double-click on `AutoTuner.exe` now
  brings that window back instead of starting a rival copy.
- *Quit* (tray menu, Quit button, Ctrl+C): always ends the process.
- The option itself is unchanged and stays opt-in under **⚙ Settings → Hide on
  close**.
