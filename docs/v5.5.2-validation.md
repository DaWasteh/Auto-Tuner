# AutoTuner v5.5.2 validation

Local checks: **2026-09-18**, Windows x64, Python **3.14.5**. Runtimes under
test: the **b11042** HIP and Vulkan trees the user built with the unchanged
Windows recipes (mainline), and the **PrismML prism-b10687** fork rebuilt
this evening by the re-pinned `ternary_bonsai_{vulkan,hip}_llama_build.ps1`
recipes (`2b_b10687_{vulkan,hip}_llama.cpp`), from the
[b11042 / prism-b10687 audit](llama-b11042-audit.md); the mainline binaries
are hashed in [llama-b11042-server-flags.json](llama-b11042-server-flags.json).

This release re-pins the Ternary/Bonsai recipes to prism-b10687, adds the
`bonsai-2-27b.yaml` profile for Ternary-Bonsai 2 27B (PTQ1_0 / PQ2_0), adds
the metadata-driven `prism.hadamard` loader gate, re-audits llama.cpp
b11030→b11042 (no CLI change) and exercises the frozen-binary, git and
source-ZIP updaters against the real GitHub release. The planner's
placement, KV and speculative logic did not change.

## Ternary-Bonsai 2 27B on the workstation (fork prism-b10687)

`bonsai_test.py` drives AutoTuner's real planner (profile match, build
gates, `compute_config`, `build_command`) for each backend × packing with
the BF16 mmproj, 32k context and Q8/Q8 K/V, then asks the running server
three things with thinking off: `17 * 23` (expects `391`), the colour of a
red 448×448 PNG (expects `red`) and the list `1 … 80` (310 generated
tokens for the decode figure). HIP single-GPU plans land on ROCm0 (R9700),
Vulkan plans on Vulkan0 (RX 9070 XT). The Vulkan figures were taken on the
workstation's primary card while it was also driving the desktop (and, at
least later that evening, a game), so they are a lower bound; the HIP
figures on the R9700 were not affected.

All 18 steps passed functionally with the same placements, splits, buffer
sizes and answers as on b11030. The **throughput figures of this chain are
not comparable to b11030**: while it ran, the workstation was also running
a game (Palworld, ~230 % CPU, on the RX 9070 XT = Vulkan0 / ROCm1) and
Discord, and the first Vulkan steps overlapped with the full pytest run and
the PyInstaller build. Single-GPU re-runs after the CPU chain recovered
(Gemma 4 Vulkan 3.9 → 58.4 t/s, Maple Vulkan 275 → 424 t/s); the two-GPU
runs (Qwen3.8 27B with a 3.7 GiB CPU-mapped remainder, Nemotron split) and
the CPU-bound Maple-on-HIP stayed slow while the game was running and are
attributed to that load, not to b11042 (no scheduler, split or kernel change
in the twelve commits; placements identical to b11030).

## Updater runs against GitHub

`update_check.py` runs the real worker classes from `qt_launcher.py`
(no GUI button, no mocks) with an isolated `AUTOTUNER_DATA_DIR`:

| Path | Run | Result |
|---|---|---|
| Frozen binary (`_BinaryUpdateWorker`), pre-publish dry run: running version forced to **5.5.0**, executable = throw-away copy of the published v5.5.1 exe with a stale marker | finds `v5.5.1`, downloads `AutoTuner-Windows-x64.zip` (70.2 MB), extracts the exe, writes and launches the detached `.bat` shim, reports "Update to v5.5.1 downloaded … restart" | **PASS** (49.7 s): the shim swapped the file (SHA-256 changed to the exact hash of the exe inside the published zip), started the new exe, its window read **AutoTuner v5.5.1**, it closed cleanly on WM_CLOSE, the shim deleted itself, `--smoke-test` of the swapped exe exits 0 |
| Git checkout (`_UpdateWorker`): fresh clone of `DaWasteh/Auto-Tuner`, `main` reset to **v5.5.0**, a local `autotuner_settings.json` | `fetch --prune`, `rev-list` ahead/behind, `pull --ff-only` | **PASS** (2.4 s): HEAD = `origin/main` (3a22037e, v5.5.1), `VERSION = "5.5.1"`, settings bytes restored |
| Source ZIP (`_UpdateWorker`, no `.git`): `git archive v5.5.0` extracted, local settings file | downloads `archive/refs/heads/main.zip`, overlays the tree | **PASS** (15.8 s): `VERSION = "5.5.1"`, settings kept, no `.git` created |

The same script was re-run after the release was published (5.5.1 →
5.5.2), all three paths **PASS**: the published v5.5.1 exe (stale-marked
copy) found `v5.5.2`, downloaded this release's `AutoTuner-Windows-x64.zip`,
the shim swapped it in 35 s (SHA-256 equal to the exe inside the published
zip), the restarted window read **AutoTuner v5.5.2** and `--smoke-test` of
the swapped exe exits 0; a clone reset to v5.5.1 fast-forwarded to
`e525803e` (`VERSION = "5.5.2"`, settings restored, 2.2 s); the `.git`-less
v5.5.1 tree was overlaid to 5.5.2 with its settings kept (15.8 s). The
published Windows asset itself passed the frozen GUI check (86 profiles,
visible **AutoTuner v5.5.2**, icons, graceful exit) and all three assets
matched their GitHub digests and architectures (`verify_release.py`). One pitfall the script hit and fixed
before the run counted: a GUI launched by the shim inherits the caller's
environment, so `QT_QPA_PLATFORM=offscreen` must not be set in the driver.

## Observed, not changed

- Vulkan runs Bonsai 2 PTQ1_0 about three times slower than HIP here (10.6
  vs 34.0 t/s, on different Navi 48 cards); PQ2_0 has no Vulkan path in the
  fork at all. The profile note says so; AutoTuner does not pick a backend.
- PrismML's fork issue #180 (Linux CPU/Vulkan PQ2_0 repack segfault) did not
  reproduce on Windows at prism-b10687; `--no-repack` is not in the profile.
- The upstream feature request for types 142/143
  ([#29058](https://github.com/ggml-org/llama.cpp/issues/29058)) is open
  without a maintainer reply; the gate stays until mainline loads the files.
- The follow-ups recorded in [v5.5.1](v5.5.1-validation.md) (Nemotron on
  Vulkan slow, Super MTP gate without a local GGUF, switch stops the old
  server before planning, CTRL_BREAK unverified) are unchanged.

The publication gates (main CI on Python 3.10–3.14 across Windows, Ubuntu,
macOS and six Linux distributions, the tag workflow's native ZIP builds and
smoke tests, digest/architecture verification of the published assets) are
the same as in [v5.5.1](v5.5.1-validation.md).
