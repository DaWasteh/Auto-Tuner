# AutoTuner v5.4.1 validation

Validation date: 2026-09-04

## Scope

This release translates every hover explanation, dialog, and Expert label
through the language packs, adds a complete Russian pack, measures whether the
tuner's memory reserves and its Q4_0 KV default cost inference speed, and acts
on the measurement with a free KV-precision upgrade plus prompt-cache reuse.
The llama.cpp authority is unchanged: stock b10797 (commit `832fd6f17`), audited
in [`llama-b10797-audit.md`](llama-b10797-audit.md); no new upstream range was
reviewed because no flag or loader contract changed.

## Translated hover help

Before this release the packs held 83 label strings, so every tooltip built by
`_setting_tooltip(summary, technical)` stayed English, and several dialogs
(`Favoriten`, `Hinzufügen…`, `GGUF-Ordner öffnen`, update and launch-error
boxes) were hard-coded German in every language.

Changes:

- `localization.setting_tooltip_html()` is the single builder of the two-level
  hover HTML; `LanguageManager.translate_tooltip()` parses it with an anchored
  regex, translates the section labels (`In short:` / `Technical details:`)
  and both plain texts, and rebuilds the HTML. Lines the GUI composes at
  runtime (`Active build: …`, `Resolved path: …`, `• balanced: …`) are matched
  by their translatable part; an appended `<br>` suffix (the environment-key
  notice on the API-key field) is translated segment by segment.
- `localization.translate()` is a module-level accessor to the installed
  manager for text Qt cannot retranslate live: message boxes, dynamic labels,
  the path-manager master checkbox, the model context menu, the `★ Favourites`
  section, and list/tree row tooltips. Changing the language rebuilds the
  model views.
- All German literals in `qt_launcher.py` became English source text, so the
  English (UK) interface is fully English.
- The catalogue grew from 83 to 427 strings per pack (344 new keys: 128
  labels/dialog texts and 216 help texts). The Dutch control-API sentence was
  reworded; the other existing translations were reviewed and kept.
- `test_localization.py` now AST-extracts every `_setting_tooltip(...)` and
  `_tr(...)` constant, the `MODEL_TOOLTIP_*` and `_FORK_TOOLTIP_*` constants,
  `_METRIC_HELP`, and the performance-target descriptions from
  `qt_launcher.py` (315 strings) and fails when any built-in pack lacks one or
  leaves a text longer than 40 characters untranslated. Two further tests
  cover the HTML round trip (idempotent on non-English, exact restore on
  English, dynamic lines, suffix) and live widget retranslation in Russian and
  French.

## Do the memory reserves cost speed?

The reserves AutoTuner withholds are: the tier safety band (0.15–0.30 GB), the
0.6 GB per-slot FlashAttention/staging workspace plus a 3–15 % long-context
guard on the KV budget, `FULL_OFF_HEADROOM_GB` (0.5 GB) before a full offload,
the MoE batch reserve (0.3/0.9 GB), and on multi-GPU systems a per-card cap of
6 % (primary) / 10 % (secondary) of total VRAM floored at 1.0/1.5 GB and capped
at 2/3 GB. llama.cpp does not run faster because more VRAM stays free, so
these reserves cost **context**, not speed, whenever the model is fully
offloaded. They cost speed only when they tip dense layers or MoE experts to
the CPU, which is exactly the trade-off the Safe/Balanced/Throughput selector
exposes (the tiers move `dense_kv_reserve_ctx`, `moe_placement_ctx_target`,
and the batch reserve). The stored benchmark records confirm the picture: on
fully offloaded models the Auto baseline (threads 12 / batch threads 16 /
1024/1024) was the measured winner in every stored run, so the runtime axes
were not where speed was being lost.

What did cost speed is the symmetric Q4_0 KV default introduced in v5.3.2.
Real `llama-bench` runs on this machine, b10797 Vulkan, AMD Radeon AI PRO
R9700 (`-dev Vulkan1 -ngl 99 -fa 1 -b 2048 -ub 512 -t 12 -p 4096 -n 64
-d 0,16384 -r 2`):

Qwen3.8-27B-UD-Q4_K_XL (hybrid GatedDeltaNet/attention, 16.34 GiB):

| K/V | pp4096 | tg64 | pp4096 @ d16384 | tg64 @ d16384 |
| --- | ---: | ---: | ---: | ---: |
| f16 | 705.4 t/s | 29.94 t/s | 613.2 t/s | 28.16 t/s |
| q8_0 | 698.8 t/s | 29.75 t/s | 602.9 t/s | 28.58 t/s |
| q4_0 | 678.2 t/s | 27.32 t/s | 539.5 t/s | 28.83 t/s |

Devstral-Small-2-24B-Instruct-2512-UD_Q4_K_XL (full attention, 13.50 GiB):

| K/V | pp4096 | tg64 | pp4096 @ d16384 | tg64 @ d16384 |
| --- | ---: | ---: | ---: | ---: |
| f16 | 858.8 t/s | 38.43 t/s | 675.0 t/s | 32.74 t/s |
| q8_0 | 839.8 t/s | 36.89 t/s | 649.3 t/s | 33.22 t/s |
| q4_0 | 805.1 t/s | 37.44 t/s | 509.9 t/s | 32.68 t/s |

Q4_0 costs 4–9 % decode speed at short context and 12–24 % prompt speed at 16k
depth; Q8_0 stays within 1–3 % of F16. Q4_0 also lowers long-context recall
quality. On both models the whole KV cache at F16 would have fit the idle VRAM
of the 32 GB card, so the speed was given away for nothing.

### Free KV precision upgrade

`tuner._pick_kv_quant()` keeps symmetric Q4_0 as the capacity baseline that
every placement step reserves for (single-GPU pinning, MoE expert packing, and
dense layer packing are unchanged). After the baseline context is known, it
takes the first of `("f16","f16")`, `("q8_0","q8_0")` whose fit within the
same KV budget still reaches that exact context. Consequences verified by the
suite:

- a 9B model with a 32k request on the dual-GPU fixture now runs F16 K/V and
  stays pinned to GPU 0 (`tensor_split 1.000,0.000`);
- the five Qwen3.8-27B fixtures keep 262,144 context; Q3/Q4/Q5 stay on the
  R9700 alone (Q8_0, Q8_0, Q4_0), Q6/Q8 keep spreading as before and take
  F16/Q8_0 in the combined budget;
- a budget that only reaches the requested context at Q4_0 stays Q4_0, and
  the profile `recommended_kv_quant` never steers Auto (OCR test updated);
- TurboQuant forks map the chosen pair through `_TURBO_QUANT_MAP`.

### Prompt-cache reuse

`build_command()` now emits `--cache-reuse 256` whenever `--cache-ram` is
non-zero. Coding agents and chat clients edit the middle of an otherwise
identical prompt (tool results, file snapshots, trimmed history), which
invalidates exact-prefix reuse; with KV shifting every unchanged chunk of at
least 256 tokens is salvaged. llama-server disables the option itself for
memory layouts that cannot shift, the flag is registered as a value flag for
dedupe and pruning, and older binaries without it lose flag and value in the
compatibility filter (tested).

## Remaining bounds

- The precision upgrade is decided from the planned KV budget; a user who
  deliberately keeps VRAM free for a second server on the same card should pin
  `q4_0` in Expert settings or lower the requested context.
- `--cache-reuse` trades exactness for speed only in the sense that shifted
  chunks are re-positioned through RoPE; llama-server refuses it where the
  cache cannot shift, and Expert `Extra CLI flags` can override the value.
- The benchmark numbers are from one Vulkan build on RDNA4; CUDA and HIP were
  not re-measured, but symmetric F16/Q8_0 pairs are supported by every
  FlashAttention backend.
