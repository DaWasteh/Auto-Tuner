# AutoTuner v5.4.9 validation

Local checks: **2026-09-14**, Windows x64, Python **3.14.5**. Runtime under
test: the **b10948** HIP and Vulkan trees from the
[v5.4.8 audit](llama-b10948-audit.md) (no new llama.cpp build in this release)
plus the user's `2b_b10616` Vulkan fork for the live GUI checks.

This release closes the three review findings that v5.4.8 documented as
deliberately open because they needed a real GUI/API session to verify.

## What changed and how it was verified

| Finding | Fix | Unit regression (`test_v549_findings.py`) | Live check on the workstation |
|---|---|---|---|
| Control API cleared its active model before the GUI decided whether it would stop the server; a rejected switch (busy, hardware pending, unknown model/runtime) then reported "no active model" while the old server kept serving | `ControlApiError`/`ControlRequest.fail` carry `backend_untouched`; every early GUI rejection sets it and `_ensure_model_locked` restores the previous active snapshot. A `clear_active()` during the attempt (the GUI stopped the server after all) wins over the restore. Rejections after the stop keep the cleared state. | Restore on an untouched 409; cleared state after `launch_failed`; `clear_active` during the attempt wins; the flag round-trips through `ControlRequest` | Agents-A1 active via `/api/v1/switch`; OCR job running; switch to a second model → **HTTP 409 `autotuner_busy`**, `/api/v1/status` still `ready` with Agents-A1, `/v1/chat/completions` without `model` routed to Agents-A1. A switch that the GUI accepted (not busy) and that then failed in planning correctly left the state idle, because the old server had already been stopped. |
| The benchmark's total time limit raised `BenchmarkFailure` and discarded every completed measurement | `BenchmarkBudgetExhausted` (not a `BenchmarkFailure`, so stage loops cannot record phantom candidate errors) ends exploration and confirmation; the decision runs on the measured candidates; `BenchmarkResult.budget_exhausted` and a reason suffix document it; only a deadline before the baseline finishes stays a failure. Diagnostic override `AUTOTUNER_BENCHMARK_DEADLINE_S` (seconds). | Deadline after the baseline keeps a valid result with no candidate errors and no confirmations; deadline before the baseline fails; the env override is honoured | Standard 12.5 % test on Qwen3.6-35B-A3B-MTP with a 240 s limit: **result saved**, "Decision: … (total time limit reached after 4 of up to 18 candidates; remaining candidates and unconfirmed finalists were skipped)". Without the override the same model completed 18/16 candidates in 25.7/22.7 min as before. |
| `/health`, `/v1/models` and `/slots` were fetched with 0.3–0.4 s timeouts on the GUI thread every 500 ms / 2 s while a model loaded | `_ServerProbeWorker` (daemon thread + queue) runs the probes; `_poll_server` only queues jobs (deduplicated per record and kind); results return through a Qt signal and `_on_probe_result` applies the unchanged ready/OCR-alias/slots logic; the worker stops with the timers on close | Worker reports health and slots off-thread and deduplicates; the window queues probes without any `urlopen` on its thread, flips ready, completes the control request, summarises slots, ignores results for stopped servers | 35B model loads and a 25-minute benchmark with many server starts: **GUI stayed fluid** (scrolling, tab changes, tooltips), "Server ready (/health → 200)" appeared as before; readiness was also reproduced against the live server on port 1234 through the real worker and signal path. |

## Observed, not changed

- A switch that the GUI accepts (AutoTuner idle) stops the active server
  **before** planning the new model. When the new model then cannot fit any
  card, the old model is already gone and the API honestly reports idle. A
  fit check against the VRAM the stopping server will free would avoid the
  needless stop; this is recorded as a follow-up, not part of v5.4.9.
- The best-effort CTRL_BREAK into llama-server's own console (v5.4.8) remains
  unverified in automation; the kill escalation and the wait before exit are
  what the tests cover.

The publication gates (main CI on Python 3.10–3.14 across Windows, Ubuntu,
macOS and six Linux distributions, the tag workflow's native ZIP builds and
smoke tests, digest/architecture verification of the published assets) are
the same as in [v5.4.8](v5.4.8-validation.md).
