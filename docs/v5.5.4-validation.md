# AutoTuner v5.5.4 validation

Local checks: **2026-09-20**, Windows x64, Python **3.14.5**. Runtimes under
test: the new **b11063** HIP and Vulkan mainline trees from the
[b11063 audit](llama-b11063-audit.md) (built by the user with the unchanged
recipes; the b11042 trees were removed) and, for the negative loads, the same
trees against the PrismML and ROCmFPX GGUFs. The fork trees
(`2b_b10687_*`, `fpx_b11544_*`) were not rebuilt and not re-measured.

This release re-audits llama.cpp (b11042 → b11063, 21 commits), records the
dedicated Ling 3.0 (Bailing V3) chat parser in `ling-3.yaml` and the nine
language packs, moves the vision + DFlash2 gate message and the
DeepSeek-V4.1 block to "b11063", and strips the new timestamped startup log
line from the `--help` capture in the audit manifest. No planner, placement,
KV or speculative logic changed.

## Ling 3.0 Flash on b11063 (`ling3_test.py`)

The local `Ling-3.0-flash-AD-IQ3_M` (two shards, 62.2 GB; `bailingmoe3`,
42 blocks, 512 experts, `nextn_predict_layers = 1`) was planned through the
real folder scan and planner (profile `ling-3.yaml`, 16k context, Q8/Q8 KV,
`--jinja --reasoning-preserve`, `--n-cpu-moe 13`, all 43 layers offloaded).
Five requests per backend; `temperature 0`.

| Check | Vulkan (planner pinned Vulkan1 main, split 22/20) | HIP (ROCm0 main, split 32/10) |
|---|---|---|
| Load | 79 s; 15.1 GiB Vulkan0, 26.7 GiB Vulkan1, 16.7 GiB CPU-mapped | 69 s; 29.1 GiB ROCm0, 12.7 GiB ROCm1, 16.7 GiB CPU-mapped |
| Parser selected (server log) | `Using specialized template: Ling 3.0 (Bailing V3)`, `chat format: peg-native` | same |
| Thinking **on**, tools offered, `tool_choice: auto` | `finish_reason: tool_calls`, `report_cache({"cache":"q8_0"})`, reasoning (103 chars) in `reasoning_content`, `content` empty | same, 23.5 t/s |
| Thinking **on**, `tool_choice: required` | tool call parsed, 22.6 t/s | tool call parsed, 28.5 t/s |
| Thinking **off**, `17 * 23` | `391` | `391` |
| Thinking **on**, "is 97 prime" | `Yes`, 665 chars of reasoning separated | `Yes`, 635 chars |
| 1…80 list (decode figure) | stopped after `11,` (36 tokens, **19.1 t/s**, `finish_reason: stop`) | 307 tokens, **29.0 t/s** decode / 72.5 t/s prompt; three list entries came out as Chinese words (十五, 数字, 罗马) |

The two parser cases are exactly the pre-#28682 failure mode (tool call
inside the pre-opened `<think>` block) and both backends now return
`tool_calls`; the profile needs nothing beyond its existing `--jinja`. The
truncated list on Vulkan and the stray Chinese tokens on HIP are
`temperature 0` decode behaviour of this IQ3_M quant, not parser or
placement faults (every other request answered as expected); they are
recorded, not fixed.

**Found on the way: the AD-IQ3_M quant has no MTP head.** Its header keeps
`bailingmoe3.nextn_predict_layers = 1` and block 41 carries attention/MoE
weights, but no `blk.41.nextn.*` tensor exists in either shard (llama.cpp
b11063's own loader calls this a *trunk-only* file). The first version of
the audit script built the entry from shard 1 alone, where the tensor scan
is deliberately "inconclusive", so `has_embedded_mtp` trusted the key and
the planner emitted `--spec-type draft-mtp`; llama-server then aborted on
both backends with `GGML_ASSERT(layer.nextn.eh_proj && "MTP block missing
nextn.eh_proj")` at `src/models/bailingmoe3.cpp:422`. The real folder scan
(`scan_models`, as the GUI/TUI use it) reads every shard, records
`__mtp_scan__ = "absent"` and `has_embedded_mtp = False`, and the planner
emits no speculative flags: that is the path the table above used. The
existing split-shard regression (`test_smoke.py`, stale nextn key) already
covers this; the script was corrected, AutoTuner was not changed.
