# AutoTuner v5.3.7 validation

Validation date: 2026-09-02

## Scope

This release reorganizes the self-contained benchmark report into a
chart-first dashboard, publishes an explicitly redacted snapshot of the
maintainer's real benchmark evidence through GitHub Pages, records total RAM in
future hardware snapshots, and rebuilds the tracked Windows executable.

Validation covers report ordering and semantics, responsive rendering, escaping
and path redaction, the committed static snapshot, least-privilege Pages jobs,
the full source suite, and the newly built frozen application.

## Diagram-first report

`performance_report.py` now renders each report in this order:

1. generated-at/version metadata and benchmark KPIs;
2. stored OS, CPU/core, GPU/VRAM, and (for new records) total-RAM snapshots;
3. fastest PP, decode, end-to-end, context, and speculative-acceptance cards;
4. per-workload aligned winner charts with one fastest end-to-end lane per
   model;
5. every successful run's candidate throughput and drafted-token acceptance
   diagrams, grouped by model;
6. the compact winner table and methodology; and
7. native `<details>` records containing facts and complete candidate tables.

The old candidate charts no longer sit inside the expandable records. The
report keeps one synchronized horizontal surface for aligned winner metrics and
bounded horizontal regions for wide candidate sets. It remains dependency-free
and uses no JavaScript.

Accessibility-focused checks cover:

- one `main` landmark and a keyboard-visible skip link;
- logical headings for dashboard, workload, model group, and run cards;
- native `<details>/<summary>` controls;
- table captions, column scopes, and keyboard-focusable overflow regions;
- unique chart descriptions and `aria-labelledby` targets;
- visible focus styling and reduced-motion handling; and
- responsive desktop/narrow layouts without replacing semantic controls.

Headless Chrome screenshots were inspected at 1440 x 1200, 1440 x 6000, and a
narrow 500 x 1100 window. The hardware, overview, aligned bars, per-run charts,
sticky navigation, and narrow KPI layout rendered as intended.

## Public export and privacy boundary

`python publish_benchmarks.py` reads the normal local performance evidence and
atomically writes only `benchmark-site/index.html`. The public renderer keeps
model filenames, benchmark labels, hardware, settings, measurements, and errors,
but does not publish model/runtime directory fields.

Public dynamic text is escaped and path-redacted before insertion. The boundary
covers:

- Windows drive paths (`C:\...` and slash variants);
- POSIX absolute paths, including `/home`, `/root`, `/tmp`, `/srv`, and
  `/Volumes`;
- UNC shares (`\\server\share\...` and `//server/share/...`); and
- `file:` URIs.

The completed HTML is then parsed with the standard-library `HTMLParser`; text,
comments, and attribute values are rescanned for every path form. The export
fails before replacing the destination if any local path or `<script>` remains.
The report's meta CSP additionally permits no script, network, object, frame, or
form source;
only inline styles and data images are allowed.

Regression fixtures inject path forms through model names, model/runtime paths,
drafter and candidate labels, decisions, errors, CPU/GPU names, and standalone
HTML validation. All are removed or rejected. HTML metacharacters remain
escaped.

## GitHub Pages boundary

`.github/workflows/pages.yml` deploys only on an explicit dispatch or when
`benchmark-site/**` / the workflow changes on `main`.

The workflow has two jobs:

- **build** checks out the repository with only `contents: read`, executes the
  static-page validation, and uploads only `benchmark-site/`;
- **deploy** depends on that artifact, does not check out or execute repository
  code, and alone receives `pages: write` and `id-token: write` before the
  official `configure-pages` / `deploy-pages` actions run.

This split prevents repository-controlled Python used for validation from
running with Pages write or OIDC credentials. No branch writer, PAT, repository
secret, custom domain, or Jekyll build is involved. The repository's Pages
source must be **GitHub Actions**; setup and future refresh instructions are in
[`benchmark-pages.md`](benchmark-pages.md).

## Publication gate

The annotated `v5.3.7` tag must point at the reviewed release commit. Before the
tag is pushed, branch `main` must contain the exact public page and rebuilt local
binary documented above. After pushing:

1. branch CI must pass;
2. the Pages source must be configured for GitHub Actions;
3. the **Deploy benchmark page** workflow must publish
   `https://dawasteh.github.io/Auto-Tuner/`;
4. the **Release** workflow must build and publish all three existing platform
   assets; and
5. local/remote branch heads and the dereferenced annotated tag must agree.

## Remaining bounds

- GitHub runners cannot access the maintainer's local `~/.autotuner` data. New
  measurements become public only after rerunning `python publish_benchmarks.py`
  and committing the changed static snapshot.
- Existing stored records predate total-RAM persistence, so this snapshot shows
  their captured CPU/GPU/VRAM data but not a synthesized historical RAM value.
- Model names, hardware specifications, timings, benchmark settings, and
  redacted error text are intentionally public. The exporter protects local path
  details; it does not make the benchmark itself private.
- GitHub Pages and Release publication remain external CI gates and are verified
  from their workflow runs after the authorized push/tag.
