# AutoTuner v5.5.8 validation

Local checks: **2026-09-28**, Windows x64, Python **3.14.5**, Core Ultra 9
285K, RX 9070 XT and Radeon AI PRO R9700. The llama.cpp runtime is unchanged:
user-built mainline **b11195 / d834d44e6** (see the
[v5.5.7 audit](llama-b11195-audit.md)).

The release integrates [issue #6](https://github.com/DaWasteh/Auto-Tuner/issues/6):
work done on a real low-memory machine (Ryzen 7 2700X, RX Vega 8176 MiB,
15.93 GiB RAM, Windows 11, llama.cpp b11223 Vulkan). The cumulative v2 patch
from the issue comment (base `c2fb891`) was applied unchanged except for the
local `Start_AutoTuner_Patched.bat`, which only started a patched source tree
next to an old EXE; the rebuilt EXE replaces it. The review below changed
the patch in six places before release.

## Integration review: changes against the v2 patch

1. **Exact expert placement stays inside the validated class.** In v2 the
   scanner's per-block expert sizes reached `_decide_moe_offload` for every
   single-file MoE on every system, not only in the adaptive branch. On a
   16 GiB GPU / 32 GiB RAM machine, plans that previously ran with a
   RAM-overcommit warning became hard refusals (for example
   Qwen3.6-35B-A3B UD-Q8_K_XL: 79,872–262,144 → "MoE weights … do not fit"),
   and 131 other plans changed. The adaptive plan now opts in with
   `__exact_moe_placement__`; every other system keeps the historical
   heuristic. Test: `test_exact_expert_placement_stays_inside_the_adaptive_class`
   (Linux, 64 GiB RAM and 16 GiB GPU variants must equal the plan without
   scanned spans).
2. **The RAM-driven expert move keeps a working context.** v2 moved experts
   to the GPU until only the compute workspace was left. On Linux 8 GiB /
   16 GiB, Gemma-4-26B Q4_0 Balanced went from 119,808 tokens (with a
   warning) to a refusal at the 2k floor. The move now happens only if it
   removes the overcommit **and** leaves a KV reservation for 8,192 tokens
   (`MOE_MIN_WORKING_CTX`); otherwise the previous plan and warning stay.
   Where both apply, the result equals v2. Tests:
   `test_ram_driven_expert_move_keeps_a_working_kv_floor`,
   `test_heuristic_low_memory_plan_is_not_refused_at_the_floor`.
3. **Launch refusal is non-modal for the control API.** v2 showed a
   `QMessageBox` when planning failed, even for `interactive=False` launches,
   and left `_last_launch_error` empty. It now uses the launch path's
   `launch_warning`. Test (real offscreen `MainWindow`):
   `test_planning_refusal_reaches_the_api_without_a_modal_dialog`.
4. **CLI:** `compute_config`'s new `MemoryError` is caught; the CLI prints the
   reason and exits 2 instead of a traceback (checked live, below).
5. **Scanner parity with llama.cpp:** expert tensors match b11195's
   `LLM_FFN_EXPS_REGEX` including `_chexps`.
6. **Hygiene:** `adaptive_memory` added to the PyInstaller hidden imports
   (it is imported inside `compute_config`); Optional narrowing for mypy;
   `ruff format` on the eight patch files (CI checks formatting); stub
   entries; plain `os` import in `verify_auto_matrix.py`.

- The runtime `n_ctx` (`/props`) equals the plan in every run. Five
  contexts are identical to the reporter's table; the other three differ
  because the reporter had 10.36–10.66 GiB free.
- Every final plan is text-only, without drafting or host prompt cache,
  with `-b 256 -ub 128`, `--load-mode none`, `--no-op-offload` and Q4_0 K/V,
  as on the reporter's machine. Gemma keeps its tied output on the CPU
  (`-ngl 30` for 30 blocks).
- The reported device buffers (model + KV + compute on Vulkan0) stay below
  the simulated 7.18 GiB free VRAM. The CPU weights (`Vulkan_Host` model
  buffer, e.g. 8.17 GiB for Gemma Safe) match the plan's estimate (8.14 GiB)
  within 0.1 GiB, and the measured drop of available RAM leaves 1.5–2.4 GiB
  of the simulated 10.4 GiB (reporter: 1.34–2.12 GiB minimum free).
- Peak private commit is 14.1–15.7 GiB. On Windows the AMD Vulkan driver
  charges device allocations to the process commit: a fully offloaded 4B
  model (8.14 GiB of device buffers) showed a 0.98 GiB working set but a
  9.31 GiB commit (`.pi/v558/commit_probe.py`). This counts against RAM plus
  page file, not physical RAM, and applies to every Vulkan plan.
- Token rates on this hardware (prompt 248–378, decode 22–46 tok/s) say
  nothing about an RX Vega / Ryzen 2700X and are only a sanity check.

## Limits

- Adaptive Auto picks the largest context. When the context is limited by
  memory, dropping vision, drafting and the prompt cache always gives a
  larger context, so on eligible systems these features are always off in
  Auto. Each dropped feature is named in the warning, preview and log; a
  "keep features above N tokens" preference would be a follow-up.
- Allocation plus a 1,932-token prompt is not a full-context workload test
  (same as the reporter); Q4 KV keeps its quality trade-off.
- The adaptive branch is validated on AMD Vulkan (RX Vega for real, RDNA4
  with a simulated budget) and only on Windows; other classes keep the
  existing planner until they are validated.
- Still open from earlier reviews: an accepted API switch stops the old
  server before the new model is planned; with honest refusals on small
  systems this is more likely to leave no server running.
